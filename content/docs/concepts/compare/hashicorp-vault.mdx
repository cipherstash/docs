HashiCorp Vault is a broad secrets-management and cryptographic platform. The closest comparison with CipherStash is its **Transit secrets engine**, which offers encryption operations without storing the application data.

CipherStash is narrower. It protects application values through the Stack SDK or CipherStash Proxy, uses ZeroKMS for split key derivation, and includes searchable-encryption support for PostgreSQL.

Vault Transit can be used in two materially different ways. A fair comparison has to distinguish them.

## Three operating models

### Vault Transit direct encryption

The application sends base64-encoded plaintext to Vault's `encrypt` endpoint and receives ciphertext. Decryption sends that ciphertext back to Vault and receives plaintext.

This keeps cryptographic implementation and key custody inside Vault, and Transit supports batched encryption and decryption through `batch_input`. The trade-off is that plaintext crosses the Vault service boundary.

### Vault Transit envelope encryption

The application asks Transit for a data key, encrypts locally, and stores the wrapped data key with the ciphertext. Decryption sends the wrapped key to Vault, receives the plaintext data key, and decrypts locally.

Vault now documents both a singular `datakey` endpoint and a plural `datakeys` endpoint for generating multiple data-key pairs. That means current Vault deployments can batch data-key generation where the endpoint is available; older comparisons that describe data-key generation as necessarily one request per value are no longer accurate.

### CipherStash ZeroKMS

ZeroKMS returns a key seed rather than a plaintext or wrapped data key. The application combines it with a client key held only in its own environment, derives a unique data key for one value, and discards that key after use.

No wrapped data key is stored with the ciphertext. The stored key ID allows the same seed to be reproduced later, but neither the ID, ZeroKMS authority key, nor client key is sufficient alone.

## Comparison

| Property | Vault direct | Vault envelope | CipherStash ZeroKMS |
| --- | --- | --- | --- |
| Where data encryption happens | Vault server | Application | Application |
| Does plaintext cross the key-service boundary? | Yes | No | No |
| Persistent per-value key material | Vault ciphertext contains key version | Wrapped data key stored with ciphertext | Key ID only; no data key is stored |
| Key-service capability | Vault holds and uses the Transit key | Vault can unwrap the data key for an authorized caller | ZeroKMS cannot derive the usable data key without the client key |
| Per-value keys | Possible through derived context or distinct keys | Possible with one data-key pair per value | Default for every value |
| Batching | `batch_input` for encrypt/decrypt | Multiple data-key generation is documented by `datakeys` | Bulk server interaction plus local per-value derivation |
| Searchable PostgreSQL fields | Convergent mode can support deterministic lookup; broader query support is custom | Requires a separate indexing design | EQL equality, ordering, range, fuzzy match, and JSON search |
| Primary operational model | Self-managed Vault or HCP Vault | Self-managed Vault or HCP Vault | Managed ZeroKMS, with client cryptography in the workload |

## The trust-model difference

Vault's security boundary is the Vault service and its operators. In direct mode, Vault receives plaintext. In envelope mode, Vault returns plaintext data keys to authorized callers. Vault can protect that boundary with policies, audit devices, key rotation, seal mechanisms, and—in Enterprise configurations—managed-key integrations.

ZeroKMS deliberately divides the boundary. CipherStash controls the authority-key side and the customer workload controls the client-key side. Neither can derive a data key alone, and the two long-lived components are never brought together.

That does not make a compromised application harmless. A live authorized attacker can use the operations granted to the workload until access is revoked. It does mean that copying the client key alone does not create a permanent offline decryption capability. The complete model is in [Cryptography](/security/cryptography#trust-model).

## Key granularity and stored material

Vault Transit keys are named service resources. Derived keys can use a caller-provided context, and envelope mode can generate distinct data keys. The application is responsible for choosing the granularity and correctly storing the wrapped key or context needed later.

CipherStash makes a unique data key per value the fixed model. The application stores ciphertext and a non-secret key ID, not a reusable or wrapped data key. ZeroKMS can reproduce the seed for that ID, but only the client key can finish the derivation.

Both systems can batch work. The meaningful difference is therefore no longer simply “Vault cannot batch data keys.” It is whether the design stores wrapped data keys and places complete unwrapping authority in Vault, or uses split control with no persistent data keys.

## Audit and revocation

Vault audit devices record requests and responses to the service, subject to Vault's documented hashing rules for sensitive fields. The event identifies the Transit path, operation, and authenticated Vault identity. How that maps to an application row depends on the key, context, and metadata design chosen by the application.

ZeroKMS ties derivation to a key ID and keyset. A client-key grant can be revoked server-side, preventing future derivation in that keyset. Federated identity and lock contexts can further bind an operation to an authenticated end user. See [Provable access control](/solutions/provable-access).

## Searching encrypted data

Vault's convergent encryption can make the same plaintext and context produce the same ciphertext, which enables limited deterministic lookup. That also exposes equality directly in the ciphertext and does not provide range, ordering, fuzzy matching, or PostgreSQL operator integration by itself.

CipherStash separates the randomized ciphertext from purpose-built search terms. The EQL domain selected for a column declares exactly which operations it supports and which structure the database learns. See [Searchable encryption](/concepts/searchable-encryption) for the leakage model and [EQL core concepts](/reference/eql/core-concepts) for the type system.

## Which should you use?

### Vault Transit is usually the better fit when

- Vault is already the organization's standard security platform;
- you need its wider secrets, PKI, signing, HMAC, tokenization, or operational ecosystem;
- direct encryption inside a tightly controlled Vault boundary is acceptable; or
- you want to own the complete key-service deployment and operational lifecycle.

### CipherStash is usually the better fit when

- the key service must never receive plaintext or possess enough material to decrypt alone;
- unique per-value keys should be the default rather than an application design choice;
- PostgreSQL must query protected fields while they remain encrypted; or
- you want key derivation, database types, SDKs, ORM wrappers, and identity binding as one system.

The products can coexist: Vault can manage infrastructure secrets and other cryptographic workloads while CipherStash protects queryable application data.
